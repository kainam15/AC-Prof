# AC-Prof 长期演进路线图（Alpha）

> 本文是长期建设优先级与验收状态的唯一入口，不是一次性优化清单，也不是自动执行调度器。
> 初始盘点基于 2026-10-31 的本地 `main`（`db2c3911`）及仓库现有文档；**实现说明不等于真实模型或硬件验收通过**。
> 技术细节仍以对应专题文档为准，本页只记录能力缺口、里程碑、决策和验证入口。

## 目标与阶段定位

AC-Prof 面向可复现的模型推理运行时画像，长期目标是让用户在支持的运行环境中完成
**模型发现 → 接口与依赖验证 → 输入/资源规划 → 正式采集 → 结果审计 → 分析与比较**。
当前处于 Alpha：优先完成真实采集闭环、通用模型适配、可扩展的 Runtime/Profiler 契约、
TUI 操作体验和可解释的科研数据，而非无止境地优化单个函数。

长期优先级：**科研正确性与安全底线 > 阻塞真实使用的缺口 > 多任务族/多平台复用能力 >
完整用户体验 > 有证据的性能瓶颈 > 局部便利性和非关键微优化**。

安全漏洞、错误测量、数据损坏与核心流程阻塞允许立即处理；处理后回到当前里程碑。
没有实测瓶颈或可验证扩展收益的锁/缓存/哈希/CSV 微优化、纯粹拆文件、极端边界补测应暂缓。
“长期建设”也不等于为抽象而重构：沿用已经足够通用的实现，只有真实扩展需求或接口障碍才重构。

## 初始能力基线与证据缺口

以下“已实现”仅指仓库中有相应代码入口或文档契约，不能推断所有模型、设备和用户流程已经验收。

| 领域 | 已存在的能力/契约 | 尚需系统性验证或建设 | 证据入口 |
| --- | --- | --- | --- |
| 模型与任务 | NLP、CV、Audio、Time series、Diffusion、Multimodal、Structured 七类任务族；声明式发现、适配与输入计划 | 区分声明支持、离线接口测试和固定 checkpoint 的真实端到端成功；新增模型不依赖 ID 特判 | [任务支持范围](models/supported-tasks.md)、[模型适配](models/runtime.md) |
| Runtime | Native Linux Docker `full` 与 Linux Process `basic` 有不同的能力和限制 | 在真实支持环境中验证生命周期、资源隔离、硬件权限和缺失指标语义；不可把 `basic` 视为 `full` | [Linux Runtime](platforms/linux-runtimes.md) |
| 采集与数据 | 统一采集窗口、输入计划、结果写入/恢复及分层结果协议 | 用真实实验确认输入、推理参数、采样窗口、指标和结果行一一对应；核对可复现性 | [采集协议](profiling/protocol.md)、[结果指标](results/metrics.md) |
| TUI | 配置、预检、进度、结果、统计/HTML 报告等交互入口；有 Textual/SVG 和 VHS/PNG 回归 | 从空配置到可解释结果的真实终端操作验收；Mock/Golden 截图不替代真实使用 | [TUI](usage/tui.md)、[PNG 视觉验证](development/png-visual-validation.md) |
| 测试与交付 | 单元、集成、视觉及硬件专项测试路径；已有代表性示例与硬件用例清单 | 建立“模型 × 任务 × Runtime × CPU/GPU × 验证级别”的可复核兼容矩阵；明确不可用/未测试 | [验证范围](development/validation-scope.md)、[`examples/hardware-validation.json`](../examples/hardware-validation.json) |
| 分析与报告 | 结果统计、独立实验比较、绘图及离线 HTML 报告 | 校验报告与原始采集、参数身份、缺失值和统计限制一致，避免跨环境误比 | [结果与分析](results/metrics.md)、[TUI 实验流程](usage/tui-experiments.md) |

**初始缺口判断**：目前最缺少的是一份跨模块、跨环境的**真实能力验收证据地图**。
不能因为测试通过、任务目录列出类型或截图正确，就把该能力标为已端到端验证。
实际缺口可能在补充验收后缩小；不要为了完成 Roadmap 人为制造重构需求。

### 验收证据级别

| 级别 | 含义 | 不能替代 |
| --- | --- | --- |
| D · 声明 | 文档、配置或能力清单存在 | 可加载、可推理 |
| T · 受控测试 | unit/mock、离线 transport、固定 TUI fixture | 真实权重、真实用户交互 |
| I · 接口冒烟 | 原生 SDK/后端与测试模型的输入、推理、输出流程成功 | 完整采集与科研指标可信度 |
| E · 真实闭环 | 固定模型 revision 在指定 Runtime 上完成加载、正式采集、结果审计和报告 | 其他平台或其他 checkpoint |
| H · 硬件语义 | E 之上，Native CPU/GPU 指标、资源限制及测量窗口得到真实硬件证据 | 未测试设备/驱动/运行环境 |

每一条“已验证”记录需标注模型、revision、任务、backend、Runtime、平台/设备、CPU/GPU、
profiling 模式、输入计划、验证级别、执行命令、日期、结果目录/验证报告和缺失指标；
无法取得证据时标记**未验证**或**受阻**，不得推测成功。

## 动态里程碑

里程碑可以并行，但任务必须有明确依赖、验收方式与适用环境；不要机械按序重写全部架构。

| ID / 优先级 | 长期能力 | 阶段性退出标准 | 初始状态 |
| --- | --- | --- | --- |
| M0 / P0 | 真实能力盘点与验收基线 | 建立代表性 checkpoint / Runtime / 任务矩阵，逐项标记 D/T/I/E/H、证据路径和阻塞原因；确定首个最小可用闭环 | **当前焦点：待验收** |
| M1 / P0 | 通用采集端到端闭环 | 至少完成受支持的 Process CPU basic 与 Native Docker full 代表性流程；保存可审计结果，明确未支持指标和恢复行为；若硬件不可得如实受阻 | 待推进 |
| M2 / P0 | 可扩展的模型与任务适配 | 在多种任务族选取非单一测试夹具的代表模型验证；新增接口优先通过已存在的声明/Adapter 注册机制扩展，并记录兼容边界 | 待推进 |
| M3 / P1 | Runtime / Profiler 组合能力 | 验证统一生命周期、能力协商、资源限制及 post-hoc 工具；按平台区分 `full/basic/unavailable`，不牺牲 Native 测量口径 | 待推进 |
| M4 / P0 | TUI 完整用户工作流 | 真实 SSH/终端完成模型选择、参数确认、预检、采集、错误诊断、结果/恢复；验证常用尺寸与中英文，辅助以 PNG/SVG | 待推进（与 M1 并行） |
| M5 / P1 | 科研数据解释与可比性 | 在代表性真实结果上核对推理参数、指标来源、实验身份、统计区间、图表和 HTML 一致性；不兼容比较有明确解释 | 待推进 |
| M6 / P2 | 安装发布与长期生态 | 从干净环境完成安装、首个实验、导出结果与排障；沉淀可维护的适配说明和发行验收 | 待推进 |

M0 是一次初始证据盘点，**不是长期优化的终点**。后续每个里程碑完成或外部模型/硬件生态变化时，
继续发现新机会、调整 M1–M6 的优先级与范围；只有证据支持的新需求才能升为当前重点。

## 自主选题与复审规则

1. **选题时**读取本页的当前焦点、状态和下一轮候选；针对目标再读对应权威专题及源码，避免每一轮通读整个仓库。
2. 选择优先级最高且依赖满足的任务，说明：真实阻塞或能力缺口、未来复用范围、验证证据、资源成本和停止条件。
3. 完成后按现有 Git/worktree 纪律提交，核对受影响功能及需要的真实证据；把“实现未验证”与“已验证”分开。
4. 更新本页的状态、已完成证据入口和下一任务。细节日志留在对应测试记录或 `internal-testing/`，不把每个小提交写进 Roadmap。
5. 里程碑完成、重大新模型/Runtime 需求出现、或约每 2–4 周进行战略复审；参考近期 Git 与真实验收结果，重新排序、合并或删除不再值得做的事项。
6. 局部非关键优化若不解决里程碑阻塞、数据正确性、安全问题或已测得的瓶颈，则记录为“暂缓”，**不自动开始下一轮微优化**。
7. 用户本轮明确任务、科研测量安全边界和项目 `AGENTS.md` 高于 Roadmap。Roadmap 只指导选题，**不会唤醒 Codex、修改现有 Goal 或启动自动续跑**。

### 维护原则

- 长期路线图只维护此页；专题定义仍由各自文档负责，技术决策与实现证据通过链接引用。
- “完成”必须有外部可核查的行为证据，而非仅有提交、测试个数或主观完成度。
- 阶段变化时替换过时的任务与证据，不无限追加历史流水账。
- 如果没有具备证据支持的高价值候选，明确报告缺口与所需决策，而不是为了持续运行制造新工作。
