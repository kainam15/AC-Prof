# 场景选择与快照验收

按本次用户可见问题选择下表的一行或相邻行。尺寸、按键与完整终端边界见[测试指南](../../../../docs/Testing.md#tui-与终端证据)；这里不复制所有控件规则。

| 改动 | 最小有意义场景 | 关键观察 |
| --- | --- | --- |
| 按钮、操作栏、长文案 | 用户尺寸、中英文、窄窗与 resize | 标签、点击面积、Tab 路径、主次操作位置 |
| 对话框、授权计划 | 长内容、键盘滚动、取消与确认 | 首尾内容可达、焦点明确、不重复启动任务 |
| 日志跟随与选择 | 持续追加时向上浏览/选择，再主动回到底部 | 不抢滚动位置、可复制、follow 状态正确 |
| CJK 通知叠加 | 开启通知，让 Toast 覆盖现有控件 | 最终 compositor/终端更新内容完整，不能只查原文 |
| 镜像树与表格拖动 | 选择、折叠、空筛选、拖动后切页/退出 | 身份与选择一致、捕获释放、长内容可达 |
| 测量状态与生命周期 | 准备→验证→测量→成功/失败，退出时仍有回调 | fixture 状态自洽、测量时停止额外刷新、结束后恢复 |
| 原生光标、颜色或宿主快捷键 | 用户实际客户端、SSH 路径、字体与终端能力 | 记录真实环境；SVG/headless 无法替代客户端确认 |

## 复用现有场景

从 [tests/visual/test_snapshots.py](../../../../tests/visual/test_snapshots.py)查已有快照，交互用例通过 `rg --files tests` 定位。复用实际应用和现有测试辅助对象，不创建平行的简化 UI 来证明产品通过。

使用临时设置与受控数据，隔离 Docker、模型加载、通知发送和正式采集边界。先确认用户报告的现象，再检查对应操作产生的可观察结果；布局事件、异步回调与动画阶段按框架机制等待，避免持续增加固定延时。

## 快照处理

1. 在现有独立快照环境运行受影响场景，保存失败差异、尺寸、语言、主题及依赖版本。
2. 查看实际 SVG/HTML 差异，区分预期变化、fixture 过期与产品缺陷。验证按钮可达、文本不截断和阶段状态一致。
3. 只更新确认过的场景，再用普通比较命令验证；不要顺手更新其它失败基线。
4. 涉及交互时保留 Pilot/按键/点击证据；涉及客户端特性时另列真实终端结果。

已有入口示例，从仓库根目录执行，按实际场景收窄范围：

```bash
acprof-snapshot-test tests/visual -q
```

快照依赖通过[辅助开发工具](../../../../docs/Testing.md#辅助开发工具)维护，不混入主项目 pytest 环境。缺少该环境时继续可用的交互检查并记录缺口，不把跳过描述为快照通过。
