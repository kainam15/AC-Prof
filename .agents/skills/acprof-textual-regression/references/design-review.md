# TUI 设计审查（按需）

AC-Prof 的界面设计以 [UI/UX 设计规范（IBM Carbon 适配）](../../../../docs/development/ui-design-system.md) 为权威依据；Carbon 提供设计语义，实际控件与显示行为按 Textual、既有主题及终端兼容性适配。

仅在新增或重排页面、改变操作路径、交互规则或视觉层级时使用。审查现有界面并按本次目标选择建议，不为套用某种 TUI 风格而重构。实际代码与测试入口以 [TUI 架构](../../../../docs/development/tui-architecture.md) 和 [场景矩阵](scenario-matrix.md) 为准。

## 按用户任务组织信息

| AC-Prof 场景 | 设计关注点 |
| --- | --- |
| 模型选择、参数与预检 | 明确下一步操作和配置是否生效；来源、下载量、资源预算等关键信息按当前能力展示，避免重复入口 |
| 准备、下载、正式测量 | 当前任务身份、阶段、进度、单位、更新时效和可执行操作清晰可见；明确区分未提供指标、零值、等待、失败、取消与完成，不制造虚假的运行状态 |
| 日志与诊断 | 控件位置稳定；手动回看时停止自动跟随，恢复跟随由用户明确操作 |
| 镜像、历史结果与详情 | 列表与详情保持稳定的角色；切换或返回时尽量保留选择、筛选与滚动位置 |
| 设置、确认与错误弹窗 | 编辑内容不意外丢失；取消、确认、失败路径清楚，弹窗接管焦点并在关闭后合理恢复 |

## 核查要点

- **优先级与空间稳定：** 首屏优先呈现当前任务最需要的状态和主要操作；减弱次要信息，不重复相同操作。页面、标签和操作栏尽量保持稳定，避免阶段变化造成位置跳动。
- **键盘与焦点：** 每项主要操作有可发现的键盘路径；Tab/Shift+Tab、方向键、Enter、Esc 的含义符合当前上下文。当前焦点与选中项可区分；帮助和操作提示只显示当前可用命令。不擅自覆盖终端保留快捷键。
- **状态与反馈：** 长时间预检、下载与处理要有可理解的进度或等待反馈；失败要指出可操作的恢复入口。异步任务不阻塞输入，但不得为改善 UI 增加正式测量期间的轮询、动画或额外采样。
- **终端与信息密度：** 在任务实际支持的窄窗和 resize 场景下，优先保留关键操作与状态，次要信息可以折叠或滚动，避免遮挡。以终端 cell 宽度校验中文、长路径、表格和不同语言，不从网页像素布局推断。
- **语义与无障碍：** 色彩、粗细、边框与文字共同传达层级，不单靠颜色或 emoji 传达状态；沿用项目主题和已有 i18n，不直接复制外部 Skill 的配色与组件方案。
- **生命周期：** 失焦、弹窗、切页、退出和失败后能够恢复键盘、鼠标与终端状态。视觉审查不能替代真实操作或测量窗口保护检查。

## 最小验收

针对本次修改说明「主要动作 → 需看见的信息 → 焦点/操作路径 → 成功与失败反馈」，再从[场景矩阵](scenario-matrix.md)选择受影响的场景进行 Pilot/快照或真实终端验证。无需为每次小改动执行全部布局、语言和尺寸组合；设计建议不等于已实现或已验证。

设计思路参考 [hyperb1iss/hyperskills 的 tui-design](https://github.com/hyperb1iss/hyperskills)（工作流驱动布局、空间一致性、键盘可发现性、渐进显示）与 [Textual 官方测试指南](https://textual.textualize.io/guide/testing/)；仅借鉴原则，不复制实现和默认主题。
