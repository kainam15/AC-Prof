# AC-Prof Docker 镜像审计

## 边界与入口

回答指定镜像是什么、为何复用或重建、哪些数据占用空间。审计保持只读；删除、改标签和清理缓存遵循用户已有授权，不把“能否删除”理解成执行删除。

当前类型与构建契约以[运行兼容](../../../docs/Runtime_Compatibility.md#镜像管理与清理)为准。只有镜像页的布局或交互问题才进入 TUI 回归；实验失败的指标与采集阶段由结果审计流程处理。

## 取证流程

1. 确定截图、模型或引用对应的 Docker 连接、daemon 身份与审计时点。先查是否有活动采集；正式测量期间不启动全盘扫描或额外 TUI。
2. 比较完整 image ID、全部标签、AC-Prof 身份标签、父层和容器引用。逻辑树节点、标签、构建 fingerprint 与 image ID 分别记录。
3. 异常重建时，对照当次日志及当前构建输入：模型 revision、文件选择、环境锁、平台、adapter 和源码身份。找出实际差异；镜像存在不代表满足复用条件，Docker 查询失败不代表不存在。
4. 空间问题分别核对镜像层、BuildKit 缓存和文件系统。按所选镜像集合去重，检查集合外引用；不累加各镜像显示大小，不把零容器引用当成零缓存引用。
5. 给出结论与证据路径。估算注明上下界、未知项和重建成本；实际释放字节只有执行已授权清理后的同口径检查才能确认。

## 按需资源

- 需要命令、重建分类或反例时读[取证分支](references/evidence.md)。
- 需要保存审计结果时使用[报告模板](assets/audit-report.md)，写到本次任务的产物目录。

## 完成标准

每个目标都有可核验身份、关系与结论；无法访问 Docker 时明确只有静态证据。若用户已授权清理，先形成具体对象清单，执行前重新检查身份与引用，完成后核对结果；未授权的对象不进入删除范围。不要将清理 BuildKit 缓存作为镜像审计的默认收尾。
