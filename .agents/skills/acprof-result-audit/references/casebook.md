# 结果审计案例与判据

以下归纳反复出现的场景；不是对任何当前结果的预设结论。先定位用户产物和本次运行版本，再按需核对[排障分类](../../../../docs/Troubleshooting.md#诊断证据)。

| 场景 | 至少需要的证据 | 不能直接推出 |
| --- | --- | --- |
| DRAM 为 `nan` / unavailable | 当次域覆盖、读取状态、配置模式及错误原因 | 模型推理失败、内存不足或能耗为零 |
| swap / Block I/O 为零 | 原始计数器是否成功读取、单位、采样窗口及容器归因 | 采集器正常或失效；两者都需要证据 |
| 容器退出 137 | 启动/请求阶段日志、容器 State、OOM 事件及主机条件 | 单凭退出码确定 OOM 或确定发生阶段 |
| 计划行数少于直觉矩阵 | 实际输入/资源计划、剪枝、warmup、repeat 与完成状态 | 固定乘法算出的缺行必然是丢数据 |
| `formal_measurement` 且有部分数值 | status、warmup、计划覆盖及各指标的适用/成功证据 | 所有指标有效或整次实验完成 |
| `disabled` 同时存在 `posthoc_backfill` | 原配置、profiler 计划、补采历史和来源身份 | 状态矛盾或补采值来自原始测量窗口 |
| 主机 perf 正常，容器 MIPS 失败 | 同工具、权限、PID namespace、目标 PID 与 attach 日志 | 主机独立命令成功已证明容器 attach 正常 |
| 长尾延迟或能耗异常 | 请求 sidecar、窗口、样本数、idle 波动及输入一致性 | 一张图或单窗口支持稳定的因果/排名结论 |

## 产物定位与完整性

沿[输出文件](../../../../docs/Profiling_Protocol.md#输出文件)读取 manifest 和目录版本，不将当前路径强加给历史结果。进行中的文件先记录审计时点，只取必要内容；部分写入与缺失文件分别说明。

复用 `audit.py` 的结构化结果，再把用户问题追到具体生产者。需要解释公式时，写明字段、来源、单位、窗口、分母和适用条件，并用一行真实数据演算。不要用内存中的旧设备状态补齐当前证据。

## 结果边界

以[CSV 分析范围](../../../../docs/Metrics.md#result_allcsv-字段解释)划分正式分析、失败边界和预热数据；适用但缺失、不适用、禁用与未验证分开记录。完整性、指标可用性和模型任务质量是三个不同结论。

需要新增适配、修复采集器或补采时，给出范围最小的下一步；用户已有修复授权则继续完成相关工作，不把只读诊断的默认边界当作反复询问的理由。
